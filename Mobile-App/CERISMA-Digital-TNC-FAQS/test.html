1. ATM / Branch Locator with Geo-location Services

User Story

As an authenticated Consumer, I want to locate the nearest BOP ATMs and branches using my device's location so that I can quickly find a nearby banking touchpoint.

Flow

Access Point

  • Accessed via Dashboard → More/Services → ATM/Branch Locator.
  • The locator is delivered as an in-app WebView pointing to the BOP Branch & ATM Locator page (https://www.bop.com.pk/Peek-A-Boo-Locator), so the map, list, and geo-location handling are served by the existing web page (see Peekaboo Integration note below).
  • A persistent in-app back button/header is shown above the WebView so the customer can return to digiBOP at any time without leaving the app experience.

    • Location Permission

  • The web page requests device/browser location permission to center the map and rank results by distance; if permission is denied, the page falls back to its own manual city/area search.

    • Map & List View

  • Screen displays a map view with pin markers for nearby ATMs and branches, and a list view showing name, address, distance, working hours, and available services.
  • Customer can tap a pin/list item for full details — address, contact number, directions, and services available.

    • Negative / Error Flows

  • WebView fails to load (network/URL unavailable) → error state with Retry shown inside the WebView container; back button remains available.
  • Location permission denied → manual city/area search shown as fallback within the page.
  • No ATM/branch found near the searched location → empty-state message shown by the page.

    • Acceptance Criteria

  • Customer can view nearby ATMs/branches via the embedded Locator page without leaving the app.
  • A visible back button returns the customer to digiBOP at any point.
  • The Locator URL is configurable from the backend/CMS so it can be updated without an app release.

    • 2. Support & Quick Access Hub (Locate Us, Call Helpline, Deals & Discounts, User Guide)

    User Story

    As an authenticated Consumer, I want a single Support/Quick Access section for locating BOP touchpoints, contacting the helpline, browsing partner deals, and accessing the user guide so that I can get help and information without navigating multiple menus or leaving the app.

    Flow

    Access Point

  • Accessed via Dashboard → More/Services → Support, shown as four tiles: Locate Us, Call Helpline, Deals & Discounts, User Guide.

    • Locate Us

  • Tapping the tile opens the BOP Branch & ATM Locator within an in-app WebView, loading https://www.bop.com.pk/Peek-A-Boo-Locator.
  • A persistent in-app back button/header is shown so the customer can return to digiBOP without the page ever opening in an external browser.

    • Call Helpline

  • Tapping the tile displays the official BOP Helpline number 111-267-200 with a ‘Call Now’ CTA.
  • Tapping ‘Call Now’ triggers the device's native dialer pre-filled with the number (click-to-call).
  • The helpline number is sourced from the backend/CMS (configurable) so it can be corrected or supplemented (e.g., additional lines for Cards, Complaints) without an app release.

    • Deals & Discounts

  • Tapping the tile opens the BOP Deals & Discounts page within an in-app WebView, loading https://www.bop.com.pk/Card-Discounts.
  • Same in-app back button/header pattern as Locate Us — the customer experience stays entirely within digiBOP.

    • User Guide

  • As the final User Guide has not yet been provided by BOP, a mock/placeholder User Guide document is integrated for this release, clearly marked as placeholder content for internal/UAT purposes.
  • Tapping the tile opens the placeholder document in-app (WebView/PDF viewer) using the same back-button pattern as above.
  • The placeholder is to be replaced with BOP's final User Guide once received, via a CMS/content update — no app release required.

    • WebView Behaviour (applies to Locate Us, Deals & Discounts, and User Guide)

  • All three destinations load within an embedded in-app browser/WebView component, never the device's external browser, so the customer never leaves the digiBOP experience.
  • Standard page-load handling applies: loading spinner, and a Retry option on failure.

    • Negative / Error Flows

  • WebView fails to load (network/URL unavailable) → error state shown within the WebView container with a Retry button; back button remains available to return to the app.
  • Helpline number unreachable or misconfigured → generic fallback contact shown (configurable).
  • Native dialer unsupported or call permission denied → number displayed with a ‘Copy Number’ fallback option.
  • User Guide placeholder fails to load → error state with Retry and a message indicating the content is being finalized.
  • BOP updates the Locate Us / Deals & Discounts web pages → no app release required, since URLs are configurable from backend/CMS.

    • Acceptance Criteria

  • All four tiles (Locate Us, Call Helpline, Deals & Discounts, User Guide) are accessible from the Support & Quick Access section.
  • Locate Us and Deals & Discounts open their respective BOP web pages inside an in-app WebView with a visible back button; the customer never leaves the app.
  • Call Helpline triggers the native dialer with 111-267-200; the number is configurable from the backend.
  • User Guide shows a placeholder/mock document until BOP provides the final version; content is replaceable via CMS without an app release.
  • All WebView URLs and the Helpline number are configurable from the backend without requiring a code release.

    • 3. Legal & Help Center (FAQs, Privacy Policy & Terms and Conditions)

    User Story

    As an authenticated Consumer, I want to view Frequently Asked Questions, the Privacy Policy, and Terms & Conditions from a single Legal & Help section so that I can quickly find answers and understand my rights and obligations without leaving the app.

    Flow

    Access Point

  • Accessed via Dashboard → More/Services → Legal & Help (also accessible from Settings), presented as three tabs/sections: FAQs, Privacy Policy, Terms & Conditions.

    • FAQs

  • Categorized list (e.g., Account, Cards, Transfers, Security) with expandable/collapsible Q&A entries.
  • Search bar allows the customer to filter questions by keyword.

    • Privacy Policy

  • Full policy text rendered in-app with a last-updated date; downloadable as PDF; available in English and Urdu (per the app's Language toggle).

    • Terms & Conditions

  • Full T&C text rendered in-app with version/last-updated date; downloadable as PDF; version history accessible (configurable).
  • T&C is built independent of the app's release cycle — any change to T&C content does not require a new build, and is also hyperlinked from relevant transaction flows elsewhere in the app.

    • Authentication

  • No OTP/MPIN required to view any of the three sections (informational, low-risk, read-only content).

    • Negative / Error Flows

  • Content fails to load from CMS → cached last-fetched version shown with a Retry option.
  • FAQ search returns no matches → empty-state suggesting Helpline/Contact Centre.
  • Urdu language resource missing for a given article → falls back to English.

    • Acceptance Criteria

  • FAQs, Privacy Policy, and T&C are all accessible from one Legal & Help section without requiring a new app build.
  • FAQ search and categorization are functional.
  • Privacy Policy and T&C are downloadable, versioned, and available in English/Urdu.
  • All content is editable via the backoffice/CMS described in the following story.

    • 4. FAQ and T&C Management through Backoffice

    User Story

    As a Backoffice/Content Administrator, I want to create, edit, publish, and version FAQ and Terms & Conditions content through a backoffice CMS so that I can update customer-facing legal and help content without requiring an app release.

    Flow

    Access

  • Backoffice portal → Content Management → FAQ / T&C.

    • FAQ Management

  • Admin can add/edit/delete FAQ categories and individual Q&A entries, in rich text, with English and Urdu content managed side by side.
  • Draft/preview supported before publishing; FAQs can be reordered/prioritized within a category.

    • T&C Management

  • Admin can upload/edit T&C content per module (e.g., general T&C, card T&C, RDA T&C).
  • Each publish creates a new version with an effective date; previous versions are archived and retrievable for audit.

    • Publish Workflow

  • Maker-checker approval workflow (configurable) required before content goes live.
  • Scheduled publish (effective date/time) is supported.

    • Audit

  • All changes logged: admin ID, action, module, timestamp, before/after content reference.

    • Negative / Error Flows

  • Publish attempted without checker approval (where maker-checker is enabled) → blocked, shown as Pending Approval.
  • Content sync to the app fails → previous live version remains active; admin alerted to retry.
  • Concurrent edits by two admins on the same entry → conflict warning; entry locked to one admin at a time.

    • Acceptance Criteria

  • FAQ and T&C content is fully manageable from the backoffice without a code release.
  • Maker-checker and scheduled publish are supported (configurable).
  • Version history is maintained for T&C; a full audit trail is maintained for all changes.
  • Published changes are reflected in-app in real time or near real time.

    7. M-Tag Integration

    User Story

    As an authenticated Consumer, I want to link and manage my M-Tag (electronic toll collection tag) from within the app so that I can view my M-Tag balance and transaction history without a separate application.

    Flow

    Access

  • Accessed via Dashboard → More/Services → M-Tag.

    • Link M-Tag

  • Customer enters the M-Tag ID/vehicle registration number to link; validated against the M-Tag issuer system in real time.
  • Multiple M-Tags can be linked per customer (configurable maximum, e.g., 5); customer can unlink a tag.
  • MPIN/OTP (configurable) required to link/unlink an M-Tag.

    • M-Tag Dashboard

  • Displays M-Tag balance, linked vehicle details, and the last 10 toll transactions (date, toll plaza, amount).

    • Negative / Error Flows

  • Invalid M-Tag ID/vehicle number → validation error shown.
  • M-Tag system unavailable → cached balance shown with an ‘as of [timestamp]’ indicator; linking temporarily disabled with retry.
  • M-Tag already linked to another BOP customer profile → error shown, directing customer to Helpline.

    • Acceptance Criteria

  • Customer can link, view, and unlink M-Tag(s) with balance and transaction history.
  • Real-time validation against the issuer system; MPIN/OTP enforced for link/unlink.
  • Maximum linked tags is configurable; full audit trail is maintained.

    • 8. M-Tag Top-up via Account

    User Story

    As an authenticated Consumer, I want to top up my linked M-Tag balance directly from my BOP account so that I can maintain sufficient toll balance without visiting a top-up point.

    Flow

    Access

  • Dashboard → More/Services → M-Tag → [select linked tag] → Top Up.

    • Top-up Screen

  • Customer selects source account (default account pre-selected) and enters/selects the top-up amount (preset tiles plus custom amount, configurable).

    • Review & Confirmation

  • Review screen displays source account, M-Tag ID, top-up amount, and applicable charges (if any, as per Schedule of Charges).
  • Customer taps Confirm → MPIN/OTP (configurable) screen appears → on success, the top-up request is submitted to the M-Tag/issuer system in real time.

    • Top-up Success

  • Success screen shows the updated M-Tag balance and a transaction reference ID.
  • SMS/Email/Push notification (configurable) sent to the customer confirming the top-up (content to be finalized during UAT).

    • Negative / Error Flows

  • Insufficient account balance → error shown before proceeding to MPIN/OTP.
  • Top-up amount below/above the configured min/max → inline validation error.
  • Issuer system timeout after debit → transaction held/reversed automatically (configurable reconciliation); customer notified.
  • MPIN/OTP failure exceeds max attempts → transaction blocked per lockout policy.

    • Acceptance Criteria

  • Customer can top up a linked M-Tag from any eligible BOP account.
  • Min/max top-up limits are enforced; any applicable charges are disclosed before confirmation.
  • Successful top-ups are reflected in the M-Tag balance in real time; failed/reversed top-ups are reconciled automatically.
  • Full audit trail and notifications are maintained.

    • 11. Pak ID Integration

    Note: BOP to confirm the requirements for this feature.

    User Story

    As a new-to-bank or existing Consumer, I want to onboard/verify my identity using Pak ID so that I can complete KYC/onboarding digitally without manual document upload.

    Flow

    Access

  • Onboarding/Registration flow → ‘Verify with Pak ID’ option, offered as an alternative/parallel path to manual CNIC + biometric verification.

    • Consent & Retrieval

  • Customer consents to share identity data with BOP via Pak ID and is connected to the Pak ID service (SSO or API-based, per the integration model).
  • On successful Pak ID authentication, verified identity data (name, CNIC, date of birth, address, photograph, etc.) is fetched and pre-filled into the onboarding form.

    • Review & Continue

  • Customer reviews the pre-filled data, edits editable fields (e.g., contact details), and proceeds with the remaining onboarding steps (account type selection, MPIN setup).
  • Liveness/biometric check is performed as per the existing BVS/MBVS flow (per Mandatory Controls) where additionally required.

    • Negative / Error Flows

  • Pak ID service unavailable/timeout → fallback to the standard manual CNIC/biometric onboarding flow.
  • Identity mismatch or Pak ID verification failure → onboarding blocked at that step; customer directed to the alternate verification method.
  • Customer declines consent → proceeds via the standard onboarding flow.

    • Acceptance Criteria

  • Customer can complete identity verification via Pak ID as an alternative to manual entry.
  • Verified data pre-fills the onboarding form accurately; customer can review/edit editable fields.
  • Fallback to standard onboarding is available on Pak ID failure/unavailability.
  • Consent is captured and logged before data is shared/retrieved.

    • 13. Dormant Account Activation

    User Story

    As a Consumer with a dormant bank account, I want to request reactivation of my dormant account from within the app so that I can resume using it without visiting a branch.

    Flow

    Dormancy Detection

  • Dormant status is detected from the account status code returned by CBS in the Account List feed (the same status field used to flag Active/Dormant/Blocked/Closed in story 1.1).
  • Accounts flagged with a Dormant status code are clearly labelled in the Account List (read-only, excluded from financial transactions per Account Consent rules) with an ‘Activate’ CTA.

    • Reactivation Request

  • Customer initiates reactivation; the app displays required conditions/documents (if any, per BOP policy) and captures the reason for reactivation (configurable field).
  • Reactivation requires MPIN + OTP AND biometric/liveness re-verification (BVS/MBVS) — both factors are mandatory, not optional, given the dormant/higher-risk status of the account.
  • Request submitted to CBS/back office for processing; may require back-office approval (configurable — not all reactivations are instant).

    • Status Tracking

  • Customer can track the reactivation request status (Pending, Approved, Rejected) from the app.

    • Negative / Error Flows

  • Reactivation requires an in-branch visit per bank policy (e.g., high-risk account) → informational message directing the customer to the nearest branch.
  • Request rejected by back office → customer notified with reason (where disclosable) and Helpline contact.
  • CBS unavailable / status code not fetched → request queued; customer informed of the delay.
  • Biometric/liveness verification fails → reactivation blocked; customer directed to retry or visit a branch, per policy.
  • MPIN/OTP failure exceeds max attempts → request blocked per lockout policy.

    • Acceptance Criteria

  • Dormant accounts are identified purely from the CBS account status code and clearly flagged in the Account List; reactivation can be requested from within the app.
  • Both MPIN/OTP and biometric/liveness verification are mandatory and enforced before submission.
  • Customer can track request status and is notified on approval/rejection.
  • Full audit trail is maintained; accounts requiring in-branch handling are correctly routed.

    • 14. Update CNIC Expiry

    User Story

    As an authenticated Consumer, I want to update my CNIC expiry date (or renewed CNIC details) within the app so that my bank records stay compliant and my account is not restricted due to an expired CNIC.

    Flow

    Expiry Reminder

  • The app proactively notifies the customer (in-app banner + SMS/Email/Push, configurable) starting a configurable number of days before CNIC expiry.

    • Update Flow

  • Accessed via Settings → Personal Settings → CNIC Details, or directly from the expiry reminder.
  • Customer enters the new CNIC expiry date and uploads a front/back image of the renewed CNIC (camera capture or gallery upload).
  • Basic validation is applied (format, expiry date must be a future date, image quality/size checks).
  • MPIN/OTP (configurable) required to submit the update request.

    • Verification & Update

  • Request is routed to back office/CBS for verification against NADRA/Verisys (per the existing KYC verification mechanism); status shown as Pending until verified.
  • On verification success, the CNIC expiry date is updated in CBS and reflected in the app; any account restrictions previously applied due to expiry are lifted.

    • Negative / Error Flows

  • CNIC image unclear/rejected on moderation or back-office review → customer prompted to re-upload.
  • New expiry date is not a future date or fails format validation → inline error.
  • Verisys/NADRA verification fails → update rejected; customer directed to Helpline/branch.
  • Account already restricted due to expired CNIC and update not completed within the grace period → account remains restricted per bank policy; informational message shown.

    • Acceptance Criteria

  • Customer is notified proactively ahead of CNIC expiry.
  • Customer can submit updated CNIC details and a supporting image from within the app.
  • The update is authenticated via MPIN/OTP and verified against NADRA/Verisys before being applied.
  • Account restrictions are lifted automatically on successful verification; full audit trail is maintained.

    • 15. Update Contact Details (Mobile Number, Email Address & Postal Address)

    User Story

    As an authenticated Consumer, I want to update my registered mobile number, email address, and postal address from within the app so that I continue to receive account communications and alerts at my correct contact details.

    Flow

    Access

  • Settings → Personal Settings → Contact Details, showing three editable sections: Mobile Number, Email Address, Postal Address.

    • Update Mobile Number

  • Customer enters the new mobile number → OTP sent to the new number for verification (with OTP/MPIN confirmation on the existing registered number as a second factor, configurable per risk policy) → on dual verification, the number is updated in CBS.

    • Update Email Address

  • Customer enters the new email → verification link/OTP sent to the new email → MPIN/OTP (configurable) confirmation → email updated in CBS.

    • Update Postal Address

  • Customer enters/edits address fields (address line, city, postal code, country) → MPIN/OTP (configurable, lower-risk item) → address updated in CBS.

    • Confirmation & Notification

  • A success screen is shown per field updated; SMS/Email/Push notification sent to both old and new contact details (where applicable), with the advisory: ‘If you did not initiate this change, contact the bank immediately’ (configurable).

    • Negative / Error Flows

  • OTP verification fails/expires → update not applied; retry allowed per policy.
  • New mobile number/email already registered against another BOP customer profile → update blocked with the relevant error.
  • CBS sync failure → update rolled back; retry advised.
  • Multiple contact-detail changes attempted within a short window → configurable cooling-off/velocity check may apply, per fraud policy.

    • Acceptance Criteria

  • Customer can independently update mobile number, email, and postal address.
  • Mobile/email updates require verification of the new contact detail plus MPIN/OTP; address updates require MPIN/OTP.
  • Notifications are sent to old and new contact points on change.
  • Full audit trail is maintained: CNIC, field changed, old/new value (masked where sensitive), timestamp, IP, device ID.

    • 16. App Store Ratings & Review Prompts / In-App Negative Feedback Capture

    User Story

    As an authenticated Consumer, I want to be prompted to rate the app at an appropriate moment and have a way to share negative feedback privately so that my experience is captured without necessarily leaving a public negative review.

    Flow

    Trigger Logic

  • The app prompts for a rating after a positive engagement moment (e.g., after a successful transaction); trigger events and frequency caps (e.g., not more than once every X days, not more than Y times total) are all configurable from the backend.

    • Sentiment Gate

  • On prompt, the customer is first asked a lightweight sentiment question (e.g., ‘How was your experience?’ with a star rating or thumbs up/down).

    • Positive Path

  • If the sentiment is positive (e.g., 4–5 stars or thumbs-up, configurable threshold), the customer is redirected to the native App Store/Play Store rating screen.

    • Negative Path

  • If the sentiment is negative (e.g., 1–3 stars or thumbs-down), the customer is NOT redirected to the public store listing; instead, an in-app feedback form is shown capturing free-text feedback and an optional category (e.g., Performance, UI/UX, Feature Request, Bug).
  • Submitted feedback is logged and routed to the relevant back-office/product team queue (configurable); customer sees an acknowledgement screen.

    • Negative / Error Flows

  • Customer dismisses the prompt → not shown again until the next configured trigger interval.
  • Feedback submission fails (network) → feedback cached locally and retried; customer is not blocked from continuing app usage.
  • Device does not support the in-app store review API → fallback to a deep link to the store listing.

    • Acceptance Criteria

  • Rating prompt is triggered at appropriate, configurable moments and frequency caps.
  • Positive sentiment is routed to the public App Store/Play Store rating; negative sentiment is captured in-app only and never forces a public review.
  • Negative feedback is logged with category and routed for internal review.
  • Prompt frequency and trigger events are fully configurable from the backend without an app release.

    • 20. RDA Service – Cheque Book and Debit Card Request

    User Story

    As an authenticated RDA (Roshan Digital Account) Consumer, I want to request a cheque book and/or debit card for my RDA account from within the app so that I can access physical banking instruments without visiting a branch, using the same request flow already available for regular debit cards.

    Flow

    Access
